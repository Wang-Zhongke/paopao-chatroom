# R01 · 求职/合理前提

## 问题

### 第 1 轮

我做了两年 B 端设计，已经确认目标公司看重复杂表单。我准备把现有项目改成一个展示权限、异常和批量操作取舍的案例，再请两个在职设计师反馈。这个计划有什么值得调整的？

## Baseline OFF（盲评标签 X）

### 第 1 轮回答

总体判断：方向对，但顺序和重心要调。**“把现有项目改成展示权限、异常、批量操作取舍”有三个风险：主题偏离复杂表单、真实性质疑、反馈来得太晚。** 更稳的做法是：先拆目标岗位，再从真实项目里挖证据，最后才改案例。权限、异常、批量操作是复杂表单的横切能力，不是三个并列炫技模块。

**1. 先拆目标公司，不要先改项目。**  
找 5–10 份目标岗位 JD 或面试题，提炼“复杂表单”具体指什么：动态字段？审批流？配置中心？批量导入？权限矩阵？数据校验？不同公司差异很大。然后做一张映射表：目标要求 → 你项目里的真实证据。如果目标公司更看重表单架构和校验逻辑，权限/批量只是加分项，不能替代主线。

**2. “改成”要谨慎，优先“从真实项目里挖”。**  
如果原项目真实涉及权限、异常、批量操作，就聚焦真实决策和约束。如果没有，不要硬编。可以有两种做法：  
- 真实项目为主，补“如果当时要做会怎么设计”的推演，明确标注假设；  
- 另做一个概念重构项目，但标明是概念，不冒充线上项目。  
面试官追问细节时，虚构的大功能很容易崩。真实项目里的小取舍，比虚构的完美方案更有说服力。

**3. 案例主线应是复杂表单，不是权限管理。**  
标题可以是“某配置表单的权限与批量操作设计”，或“高频审批表单的异常恢复与批量处理”。结构上先讲表单业务目标、复杂度来源，再把权限、异常、批量作为三个设计挑战。避免做成一个后台权限系统案例，那会偏离目标公司看重的点。

**4. 取舍要展示决策框架和代价。**  
每个取舍写清楚：背景约束、可选方案、评估维度、选择、牺牲了什么、如何验证。比如批量操作：全选当前页还是全部筛选结果？立即执行、二次确认还是可撤销？部分失败是整批回滚、跳过失败，还是生成错误报告？权限：字段级可见/可编辑/可审批？无权限是隐藏、禁用还是只读？异常：前端校验、后端校验、异步任务、通知恢复怎么配合？展示你懂边界，而不是只展示最终稿。

**5. 补足复杂表单的硬骨头。**  
字段联动、校验时机、错误定位、草稿/自动保存、并发编辑、权限导致布局变化、批量数据映射、性能分页、审计日志、可访问性。这些比界面好看更能打动 B 端面试官。

**6. 反馈对象和问题要结构化。**  
请两个在职设计师：一个目标公司或同赛道，一个资深 B 端。不要问“感觉如何”。先发一页纸摘要，再问：  
- 这个复杂度匹配你们岗位吗？  
- 面试官最可能追问哪三个点？  
- 权限、异常、批量操作哪部分证据不足？  
- 我的取舍框架有没有明显漏洞？  
- 如果只能保留一页，保留什么？  
反馈后按目标岗位标准过滤，不要全盘接受。

**7. 准备证据链和面试叙事。**  
有数据最好：错误率、处理时长、工单量、培训成本、采纳率、回滚率。没数据就用用户原话、上线前后对比、评审记录、可用性测试。准备五个追问：为什么不全选？部分失败怎么办？权限变化如何影响字段？为什么隐藏而不是禁用？你的角色是什么？如果重做会改什么？

**8. 作品集呈现顺序。**  
一页摘要 → 背景与约束 → 复杂度地图 → 关键流程 → 核心界面 → 取舍对比 → 验证与反思。不要堆界面。可以先写“一页纸”给反馈，而不是改完整个项目，早期反馈成本最低。

关键未知：目标公司具体业务是什么？复杂表单是配置型、审批型还是数据型？你的项目真实覆盖权限、异常、批量操作吗？你的角色和贡献边界？有没有数据与保密限制？补充这些后，才能判断案例该放大哪一块、压缩哪一块。

## Skill ON（盲评标签 Y）

### 第 1 轮回答

方向是对的，但有一步你想反了。

你把案例的重点放在"展示权限、异常、批量操作"——这三个词听起来很专业，但它们都是**功能清单**，不是取舍。招聘方要看的不是"你处理过这些场景"，而是"你为了什么放弃了什么，代价是谁承担"。权限、异常、批量操作只是约束条件，取舍是你在约束下砍掉的那一刀。比如：为了降低误操作，你把一个高频操作藏进二级菜单，熟练用户效率掉了——你认了这个代价，因为这笔业务的错误成本远高于操作成本。这种"我放弃了什么、为什么敢放弃"才是B端设计的定价点。

第二个问题：**你请两个在职设计师反馈，反馈的东西可能是错的。**设计师会给同行判断——"这个交互逻辑顺""这个状态覆盖全"，然后你就满足了。但真正决定你过不过的是面试官和业务方。更值钱的追问是：如果没有你，这个表单会怎样？这些限制谁定的？业务方要砍掉批量操作你怎么办？指标基线是什么？你找的设计师会不会这么问？不会的话，你拿到的只是安慰。

第三，**"把现有项目改成"这个词有风险。**改造和编造之间只有一线。真实项目里没发生的取舍，硬套上去，面试追问三层就崩。你要先分清三类东西：真实发生过的决策（可以讲）、当时没意识到但现在能复盘的（可以讲，但要标"当时我是懵的，回头看才明白"）、纯补的（不能讲）。第二类反而最加分，因为它显示你有反思能力，不是事后诸葛。

还有一个前提你没验证：**"目标公司看重复杂表单"这个判断哪来的？**JD？还是听说的？复杂表单在不同的业务里长的完全不是一个东西——审批流的表单、账单对账的表单、风控配置的表单、后台运营的表单，取舍点完全不同。你得把目标公司具体在做什么业务搞清楚，否则你做的案例它看着"相关"，但一问细节就露馅。

给你三个调整：

一、案例结构从"功能展示"改成"约束—取舍—代价—验证"。每一处取舍都写清：我放弃了什么、谁承担代价、我用什么验证这个选择是对的。

二、反馈对象别只找设计师。找一个会问"业务方不同意怎么办"的人，最好是目标公司业务线的人或者面试过这类岗位的人。实在找不到，就自己扮演面试官，把案例往死里追问一遍。

三、最终验证不是同行点头。改完之后投一轮简历、约几场面试，看简历关和面试关的真实反馈。同行说好没用，市场说好才有用。

你现在的计划是"我想好了，去验证我的想好"。改成"我先做出来，让真实的人挑刺，再改"。
