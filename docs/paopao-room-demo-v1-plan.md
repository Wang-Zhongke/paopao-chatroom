# 泡泡连麦室 Demo v1：产品与交互方案

日期：2026-09-17。状态：设计讨论稿；没有开始开发，没有调用付费 LLM API。

## 1. 产品定义

用户带着一个具体职业困惑进入，在泡泡老师公开表达所形成的思考与说话方式下进行连续交流，逐步弄清关键变量，带着一个明确判断和下一步行动离开。

首版成功体验：用户感觉自己的具体情况被听进去，对话有推进，并能说明接下来要验证什么。

主要体验场景：有工作经验，正在考虑转 AI、换工作、选择 Offer 或开始做内容的人。入口优先展示转 AI、换工作、做内容三个例子；其他 Skill 覆盖的问题仍可自由输入。

主标题：泡泡连麦室。
主文案：你最近，在纠结什么？
输入提示：比如：做了五年运营，想转 AI 产品，但一直在学工具，还没做出项目。
开始按钮：开始聊。
入口一处简短身份说明：基于泡泡老师公开内容的 AI 视角体验。对话里维持第一人称和人物节奏。

## 2. 已确定与暂定的范围

已确定：

- 首个项目是连麦室，职业手牌在后续版本加入。
- 所有 LLM 生成使用 DeepSeek Flash。
- 前端设计遵循 frontend-design，采用针对像素范与连麦场景的独立视觉。
- 当前任务只梳理逻辑和方案。

暂定：首版采用文字流式连麦。已向用户询问是否首版需要真实语音，等待答复；下文默认文字版。如果改为语音，保留相同对话逻辑，另补语音识别、播报、轮流发言与打断设计。LLM API 本身不等同于完整语音通话系统。

首版包含：

- 单一连麦空间、自由输入、三个可编辑的开场示例。
- 连续对话、流式生成、停止回复、失败重试。
- 同设备历史记录、恢复会话、新开一场、删除记录。
- 用户主动生成连麦小结；小结可以编辑、复制、导出文本。
- 按需要展开的相关公开内容入口。
- 桌面和移动端布局。

后续加入：真实语音、职业手牌界面、附件解析、跨设备账号、公共分享、支付、实时联网研究。首版不展示尚未可用的功能按钮。

## 3. 一次连麦如何推进

路径：开场描述 → 初步回应 → 关键追问与讨论 → 当前判断 → 连麦小结 → 实际行动后回来续聊。

这是对话可能经历的阶段，不是用户必须走完的固定问卷。信息完整时直接给判断；用户只想简短回答时不强行延长。

### 开场

用户先自由描述，不填写年龄、学历、城市等长表单。示例按钮只填入输入框，用户可修改后发送。

第一轮先回应用户具体说了什么，给一个初步观察。缺少关键事实时，再问一个会改变判断的问题。用户前提合理时直接承接；不用强行“你想反了”制造人物感。

### 追问与判断

- 分清修辞反问与信息追问：修辞反问后继续解释；真正需要用户提供事实的问题才停下来等回答。
- 每轮通常集中在一个关键问题，可包含紧密相关的小问，不逐项盘问。
- 已经回答过的内容不重复询问。
- 用户修正事实时，更新当前判断，必要时自然承认“那这个判断要改一下”。
- 用户说“直接给结论”时，基于已有信息给当前倾向，并讲清哪个未知事实可能使结论反转。
- 用户说“不知道”时，给可获取事实的办法，或者带着明确假设继续分析。
- 用户转移话题时，允许自然转向；明显成为另一件事时提供“另开一场”，但不自动丢失原对话。

短回答为默认节奏：几个口语段落，先给有用判断，再举例或追问。长度随问题变化，不把字数或轮数写成死规则。复杂问题可展开，普通回答不自动套报告栏目。

### 连麦小结

用户随时可以点“整理这次连麦”。信息不全也能整理，缺口如实留空。

小结只呈现：你正在决定的事、当前判断及理由、需要确认的事实、下一步行动。存在可携带经验时可自然写入正文，首版不生成卡牌、能力分或职业等级。

小结生成后仍可继续聊。对话有新内容时提示“小结有新内容可更新”，不默默覆盖用户手动编辑的内容。

## 4. 一段示意对话

以下是产品交互示例，不是泡泡老师原话。

用户：我做了五年运营，想转 AI 产品，最近在学 MCP 和 Agent，但还没项目。

回应：你这五年运营经验，先别急着清零。公司要找的是能把业务问题做成产品的人。你现在的工作里，哪件事最重复、最耗时间，而且你确实清楚它为什么这么做？

用户：每周整理客户咨询，再交给产品经理排需求。

回应：那这件事就有东西可以做。你同时接触客户问题和产品决策，比单独学工具更接近产品工作。现在最费时间的是把咨询分好类，还是分完之后没人知道该优先解决什么？

用户：后者，我们分了很多类，但没人用。

回应：那我前面的方向要收窄。再做一个自动分类器，很可能只是更快地产生没人看的表。先拿最近一批咨询，和产品经理一起确认：什么信息能让他改变一次需求排序？把这个判断过程做出来，你才有项目的起点。

重点：后续回应使用新增事实，建议可能改变，不把开场结论反复改写。

## 5. 前端视觉方案

### 概念：像素工作室里的线上答疑台

识别元素集中在一个原创像素泡泡角色。周边像专业设计师的工作台，保持清楚、干净，用户内容是主要视觉重量。

比较过两个方向：完整复古游戏机容易让职业讨论变得幼稚；仿直播间容易引入假观众、弹幕和无意义状态。选择轻量像素角色与答疑空间，像素只用于角色、标志和少量状态细节。

颜色：

| 名称 | 色值 | 用途 |
|---|---|---|
| 工作台银灰 | #EEF1F6 | 页面背景 |
| 纸面白 | #FFFFFF | 阅读区域、输入区 |
| 深海墨蓝 | #182744 | 正文、主标题 |
| 像素钴蓝 | #3157D5 | 主要按钮、焦点与本人消息标识 |
| 泡泡浅蓝 | #DDEAFF | 用户消息背景、轻量选中状态 |
| 提醒橘 | #D45B3F | 少量需要注意的状态；不作大面积装饰 |

字体：中文选 Noto Sans SC，系统中文黑体作回退。标题用较重字重，正文用常规字重；正文不使用像素字体。建议正文 16–18px、行高约 1.7；大标题约 36–48px，移动端约 30px。对话阅读宽度控制在约 32–38 个汉字。

布局：桌面左侧窄栏放角色与会话入口，中间给足对话宽度；整理小结时才出现右侧抽屉。移动端会话列表收入菜单，小结独立滑出。正文左对齐，开场标题与输入区域也以左对齐为主。

桌面草图：

```text
┌──────────────────────────────────────────────────────┐
│ 泡泡连麦室                              本次小结      │
├────────────┬─────────────────────────────────────────┤
│ 像素泡泡   │  你最近，在纠结什么？                    │
│            │                                         │
│ 新开一场   │  说说你的处境，先从最纠结的地方开始。    │
│ 最近连麦   │                                         │
│            │  用户：做了五年运营……                    │
│            │  回应：你这五年经验，先别急着清零……      │
│            │                                         │
│            │  [补充你的情况……             ] [发送]   │
└────────────┴─────────────────────────────────────────┘
```

动效：发送、停止、展开小结和角色回应时才有短反馈。接收流式文字时滚动跟随，用户向上阅读后停止自动拉回。减少动态偏好下关闭装饰动作。

真实状态文案：正在回复、回复已停止、连接中断，重试。没有真实语音时不放麦克风、音量波形和正在收听提示。不要展示假排队人数、假在线观众、模型名和技术处理阶段。

## 6. Skill 如何进入产品

DeepSeek API 不会自动读取本地 Skill，也不会因为请求包含一个路径就理解整套资料。服务端必须组织实际提示内容和上下文。

计划使用三个层次：

1. 人物基础：当前 Skill 的人物模式、心智模型与 Expression DNA。保留公开内容对应的思维顺序和表达重心。
2. 场景材料：按职业、AI、求职、品牌、商业、设计选择相关 framework。先用轻量主题匹配，跨域自然组合；后续根据真实错误再调整。
3. 当前对话：用户原始消息、近期上下文及必要摘要。用户事实优先使用原始消息；推测与用户陈述分开记录。

应用层只补充连麦交互要求：回应已有信息、适时追问、短轮次节奏、可停止和可整理小结。原 Skill 继续作为独立资料源，不为适配网页重写其观点。

353 条视频用于按需检索，不整批塞进每次请求。首版可复用本地主题索引和关键词检索，优先检索来源卡片，再读取相关转录上下文。当前 `search_corpus.py` 是正则检索脚本，可以参考其出处定位方式，但它不是已经部署好的检索服务。

展示的原视频链接由服务端从已知来源记录构造，模型只能引用传入的来源 ID。来源抽屉写“相关公开内容”；只有实际支持当前论点的材料才标为该论点依据。没有匹配材料时不补一个看似相关的链接。

## 7. DeepSeek 与技术安排

核验日期：2026-09-17。

- 官方当前推荐模型名：`deepseek-flash`。
- 官方 OpenAI 兼容地址：`https://api.deepseek.com`。
- 对话使用 Chat Completions 的流式输出。
- 普通交流先以低思考强度作为候选，复杂比较再测试较高强度；实际取值在开发时依据人物表现与首字延迟确定，不预先承诺速度。
- 整理小结可使用单独的结构化输出请求；校验失败可重试，失败不影响已经完成的对话。
- 不向用户展示模型内部推理；展示最终回复和真实来源。

候选实现：Next.js + TypeScript，服务端调用 DeepSeek，浏览器使用 IndexedDB 保存单设备对话。首版无账号、无服务器持久化职业档案。API key 仅放服务端环境变量，原始研究目录不作为网站静态资源公开。

正常一轮以一次生成请求为主；检索在本地完成，不增加 LLM 路由链。只有用户点击整理小结时，才额外调用模型提取结构化信息。长对话需要压缩时保留近期原文、重要事实对应的消息 ID 和修改记录。

本地保存不意味着离线：生成回复时相关对话会发送给 DeepSeek。设置里提供删除本地记录与导出；首版服务端日志只保留排错所需状态，避免默认写入完整职业对话。

当前事实：首版没有联网搜索。遇到最新薪资、具体公司状态、工具最新能力等问题时，用用户提供的材料做条件分析；需要核验的事实明确留待核验，不把模型记忆当成实时搜索结果。若最新事实成为常用需求，再加入研究接口。

失败体验：

- API 未配置：明确显示尚未配置，禁用真实发送；不以预制回答冒充成功接入。
- 网络中断：保留用户输入和已生成部分，提供重试。
- 用户停止：中止请求、保留部分回复并标记未完成；未完成内容不作为已定判断写入小结。
- 同一会话生成中不并发发送多条，用户可停止后补充。
- 小结失败：原对话可继续使用，允许重新整理。

## 8. 给职业手牌保留什么

首版以会话为中心，不提前设计卡牌等级或能力评分。

保存基础对象：

| 对象 | 首版内容 | 后续用途 |
|---|---|---|
| 会话 | ID、标题、时间、主题、消息 | 职业档案的经历来源 |
| 消息 | ID、角色、正文、时间、完成状态 | 判断原话、修正事实、回溯证据 |
| 小结 | 当前问题、目标、约束、选项、判断、待确认事实、行动 | 阶段决策记录 |
| 经历线索 | 用户提到的项目、结果、技能、行业经验，附消息 ID | 候选职业手牌 |
| 行动反馈 | 用户后来尝试了什么、发生什么，附消息 ID | 卡牌更新与项目复盘 |
| 来源 | 公开材料 ID、原链接、时间位置、质量标记 | 核对人物归因 |

“用户说自己做过”“AI 推测有某能力”“已有项目证据”分别保存。用户纠正一条经历后，后续小结使用新版本，旧值留作已被取代的信息。职业手牌阶段再让用户确认哪些经历值得形成卡牌。

为可复现性记录 Skill 版本、模型 ID、应用提示版本及检索来源 ID。它们用于开发排查，不占用正常对话界面。

## 9. Demo 的验收方法

产品目标：一位新用户能够从输入困惑开始，完成连续交流，得到有用小结，并在刷新后继续。

行为检查使用真实 DeepSeek API：

- 信息不足会追问关键事实，信息足够时直接回答。
- 后一轮真的使用用户新增内容，允许修改原判断。
- 职业、AI、Offer、设计、自媒体问题各有不同变量和例子。
- 保持人物声音，但不会对每个合理问题强行否定或编造用户动机。
- 不显示内部模型名或研究标签，自设行动周期不冒充公开固定公式。
- 用户纠正、停止、断线和小结失败都能继续使用。
- 小结及经历线索能回溯用户消息，不把推测写成用户事实。
- 桌面、移动端、键盘操作和减少动态设置均可用。

少量同模型 A/B 对照用于检验 Skill 是否改善对话推进和人物辨识度；单独记录泛泛建议、机械犀利、重复追问与归因错误，不只给综合分。

首字延迟、完整回复耗时、单轮用量在真实调用后报告，目前没有性能和成本实测。

## 10. 后续开发顺序

1. 确定文字/语音范围，审阅本方案与视觉方向。
2. 制作可点击的入口、对话、小结三个状态，校准读写体验。
3. 接 DeepSeek 与人物上下文，验证连续对话。
4. 加入相关材料检索、历史恢复、小结导出与失败处理。
5. 真实体验测试后收敛首版。
6. 再把已经积累的经历与行动反馈转为职业手牌。
